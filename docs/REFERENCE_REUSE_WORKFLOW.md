# 레퍼런스 재사용 워크플로

이 문서는 PC에서 보는 HTML Scroll/Slide 자료의 **작업 순서와 참고 자료의 역할**을 정합니다. 토큰은 [디자인 시스템](../DESIGN_SYSTEM.md), 도식 제작은 [Figure 표준](FIGURE_PRODUCTION_STANDARD.md), 실제 데이터·수식은 [페이지 상세 명세](REFERENCE_PAGE_SPECS.md)가 기준입니다.

## 무엇을 먼저 보는가

| 순서 | 자료 | 역할 |
| --- | --- | --- |
| 1 | AGENTS / 사용자 요구사항 | 범위·우선순위·저장소 규칙 |
| 2 | DESIGN_SYSTEM + DESIGN_COMPONENT_RECIPES | 로컬 Pretendard·−1pt·행간/간격·프레임·카드·패턴별 수치/예외 |
| 3 | TEMPLATE_CATALOG | 청중과 내용에 맞는 패턴 선택 |
| 4 | FIGURE_PRODUCTION_STANDARD | 의미·기하·좌표·검증 절차 |
| 5 | REFERENCE_PAGE_SPECS + 관련 상세 패턴 | 데이터·식·조건·삭제 금지 정보 |
| 6 | 실제 HTML/CSS/SVG/JS | 구조적으로 재구성할 편집 원본 |
| 7 | 최신 Chromium 프리뷰 | 시각적 품질 비교·검수 증거 |

프리뷰를 슬라이드에 붙여 원본을 대신하지 않습니다. 모든 자료에 8개 패턴을 순서대로 넣지 않습니다.

## 새 Scroll / Slide 자료 만들기

1. 청중·선수 지식·한 줄 목표를 정합니다. [용어 첫 등장 기준](../DESIGN_SYSTEM.md#용어와-약어의-첫-등장)에 따라 독립 학습 단위와 새 용어의 정식 명칭·짧은 뜻·첫 설명 위치·이후 약어를 기록합니다.
2. Scroll(목차·상세·실습) 또는 Slide(16:9·한 장 한 메시지)를 고릅니다.
3. 입력·처리·출력·단위·수식·실측/예시 구분을 설계 시트에 기록합니다.
4. 카탈로그에서 가까운 패턴을 선택하고 실제 원본을 엽니다.
5. [컴포넌트 규격](DESIGN_COMPONENT_RECIPES.md)의 설계 기록표에 패널·Typography·간격·도식·수식·상태·PC 창 대응·예외와 높이 예산을 작성합니다. 공통 CSS와 폰트 자산·라이선스를 포함하고 다른 위치로 복사하면 로드 순서·상대 경로를 확인합니다.
6. 실제 과제의 데이터·라벨·식·Shape·색 의미를 함께 바꿉니다. 원본에 약어가 있다는 이유로 이미 설명됐다고 가정하지 말고, 새 독자와 읽는 순서에 맞춰 보이는 정의를 배치합니다.
7. 도형을 배치한 뒤 실제 경계로 화살표와 중앙축을 계산합니다.
8. PC 4개 크기(1600×950/1440×810/1366×768/1280×720)에서 배치를 조정하고 독립 계산·실제 폰트·잘림·Footer를 검사합니다.
9. 다른 데이터 구성이나 경계값에서 재사용을 검증합니다.
10. 소스·상세 명세·카탈로그·프리뷰·검증 JSON을 같은 구현으로 맞춥니다.

## 그대로 유지할 원칙과 바꿀 내용

유지할 것은 역할 구분·수식과 Figure 대응·정렬·토큰·검증 수준입니다. 사진·숫자·CNN 단계·3분류 같은 예제 전용 내용은 실제 목표에 맞게 바꿉니다.

예를 들어 #5는 고정된 실제값 그룹과 바뀌는 예측의 관계를 재사용합니다. #6은 모듈·차원·내부/외부 변환의 구분을 재사용합니다. 새로운 문제의 데이터가 많으면 기존 한 장에 억지로 넣지 말고 Scroll 또는 여러 슬라이드로 나눕니다.

## 소스에만 남는 디자인 값 방지

새 CSS 값을 추가할 때는 역할을 공통 기준·역할별 변형·예제 전용·새 예외 중 하나로 정합니다. 공통 토큰이 있으면 재사용하고, 전용 수치이면 페이지 명세에 값·이유·PC 창 크기별 변화를 기록합니다. 예외 때문에 공통 파일을 수정할 때는 영향을 받는 페이지와 검증 범위를 기록합니다.

리뷰 전에 설계 기록표를 소스와 대조합니다. 특히 `line-height:normal`의 암묵적 의존, 제목/소개/첫 단계의 서로 다른 간격, `margin-top:auto`가 소비하는 공간, 분수/긴 식의 높이, 카드 패딩·border, 그림 실제 경계, 축/단위/범례, PC 창 축소 시 연결·줄바꿈과 실패 상태를 확인합니다. 같은 숫자라도 의미가 다른 항목을 한 토큰에 억지로 묶지 않습니다.

## #2·#3의 계산 모티프와 #6 구조 그림

- #2 Process / #3 Comparison은 `assets/cnn-feature-maps.js`에서 같은 사진을 64×64 휘도로 바꿔 고정 방향성 필터 16개와 ReLU를 계산합니다. 대표 채널 4개를 표시하며 학습된 모델의 추론이 아닙니다.
- #6 Architecture는 별도의 SVG 모식도입니다. 최종 흐름은 두 Conv/ReLU/MaxPool Block → Flatten 8,192 → FC → Softmax입니다. 사진에서 계산한 #2·#3의 특징 배열이나 실제 추론 확률과 같은 데이터라고 설명하지 않습니다.
- 예제의 작은 그림 격자·대표 평면·생략 셀과 실제 H/W/C·벡터 차원을 구분합니다.

## 재사용 검증의 증거

#5 검증은 실제값 비율 3:3을 4:2로 바꾸고 한 점수를 임계값과 같게 만들어, 그룹 구성·예측·행렬·백분율·대입식이 함께 맞는지 확인합니다. 기본 예제의 통과 결과를 새로운 임의 데이터의 검증으로 주장하지 않습니다.

새 자료에서는 조건에 맞는 다른 데이터를 하나 이상 선택합니다. 행렬은 독립 계산, 모델 구조는 Shape 계산, 비교 그래프는 단위·정규화, 인터랙션은 경계값·분모 0을 확인합니다. 변경한 원본에서 실제 Chromium 캡처를 생성합니다.

## 문서와 Git 작업

별도 브랜치에 범위를 좁혀 작업하고 사용자 변경사항을 보존합니다. 충돌은 파일의 날짜나 PR 번호만으로 결정하지 말고 실제 기술·시각 결과를 비교합니다. 사용자에게 승인된 범위 안에서 Commit·Push·PR을 진행하고, main Merge에는 명시적인 승인이 필요합니다. 이번 통합처럼 세션에 이미 Merge 승인이 있으면 검증 후 그 승인 범위 안에서 진행합니다.

최종 답변에서는 로컬 Commit, 원격 Push, PR, main 반영을 구분합니다. 인증·검증이 막힌 상태를 완료로 보고하지 않습니다. [현재 상태](REFERENCE_RELEASE_STATUS.md)는 8종 출처와 검토 완료 상태를 보여줍니다.

## Scroll / Slide 공통 원본의 실제 적용 예

[두 보기의 재사용 명세](DUAL_MODE_REFERENCE_REUSE.md)는 기존 8개 HTML을 직접 실행하여 디자인 복사본 없이 표시하는 예제입니다. Scroll/Slide는 보기와 탐색만 다르고, 실제 그림·스타일·계산은 같은 원본이 담당합니다. #5 실습은 두 모드의 기능이며 세 번째 형식이 아닙니다. 원본 스타일과 상대 bounding box를 직접 렌더링과 대조하고, [모드 계약](../templates/dual-mode-learning/MODES.md)에 따라 현재 예제와 임계값을 유지합니다. 새 강의에 모든 8개 유형이나 iframe 구현을 강제하는 규칙은 아닙니다.

[로지스틱 회귀 본편2장·선택 부록](../examples/logistic-regression/README.md)은 이 절차로 **새 내용**을 만든 사례입니다. 설계를 먼저 Commit하고 본편에는 Concept/Step-by-Step을 선택했습니다. 임계값 Interactive는 확률 계산의 필수가 아니므로 `?appendix=1`의 선택 부록으로 분리했습니다. 같은 DOM 생성·모델을 두 모드가 공유하며 iframe·사진·CNN 도식을 강제하지 않습니다.

**재사용 검증을 위해 유형 수나 장 수를 채우지 않습니다.** 본편의 학습 목표에 필수인 단계만 선택합니다. 후속 응용은 필요하면 선택 부록으로 명확히 구분하고 기본 페이지 수·목차·탐색에 끼워 넣지 않습니다. 본편/부록 선택은 Scroll/Slide의 제3 출력 형식이 아니며 같은 두 진입점의 콘텐츠 범위입니다.
